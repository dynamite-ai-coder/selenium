Build a complete production-ready web application that runs on Render and provides a Browser Use-style AI agent with a web chat interface and a live GUI browser preview.

Main goal

Create a web application where a user can:

1. Open the application URL hosted on Render.
2. Authenticate with a password.
3. Enter instructions in a ChatGPT-style chat interface.
4. Send the task to an AI browser agent.
5. The AI agent uses DeepSeek via API key as its LLM.
6. The agent controls a real Chromium/Chrome browser.
7. The browser runs in GUI/headed mode, not headless mode.
8. The user watches the browser live through an embedded browser preview/noVNC interface.
9. The AI navigates websites, clicks buttons, types into fields, scrolls, reads pages, and completes normal browser automation tasks.

Technology

Use a reliable Python-based architecture.

Preferred stack:

- Python 3.11+
- FastAPI
- Uvicorn
- Browser Use
- Playwright/Chromium as required by Browser Use
- DeepSeek API
- noVNC
- Xvfb
- XFCE
- WebSocket communication
- HTML/CSS/JavaScript frontend

Do not use Selenium unless Browser Use specifically requires it. Prefer Browser Use with Playwright.

Render compatibility

The application must:

- listen on "0.0.0.0:$PORT"
- work correctly with Render Web Services
- include a "Dockerfile"
- include "render.yaml"
- include "requirements.txt" if appropriate
- include all required startup scripts
- automatically start the virtual X display
- automatically start XFCE
- automatically start Chrome/Chromium
- automatically start noVNC/websockify
- automatically start the FastAPI server

The container must not require SSH or manual terminal commands after deployment.

Use a single Render service unless there is a strong technical reason to split components.

Authentication

Protect the entire web interface with a password login page.

Default password:

"Dupa1234@"

IMPORTANT:

Do not hardcode the password directly into application logic.

Use:

"APP_PASSWORD"

as an environment variable.

For local development, provide a ".env.example" containing:

"APP_PASSWORD=Dupa1234@"

The application must reject unauthenticated access to the chat and browser preview.

Use secure HTTP-only session cookies or another appropriate server-side authentication mechanism.

Do not expose the password in frontend JavaScript.

DeepSeek integration

Implement DeepSeek as the primary LLM provider.

The API key must be configurable through:

"DEEPSEEK_API_KEY"

Do not hardcode the API key.

Also make the DeepSeek model configurable through:

"DEEPSEEK_MODEL"

Use a sensible current DeepSeek model by default, but allow the user to change it through the environment variable.

The implementation must use Browser Use's supported DeepSeek/OpenAI-compatible LLM integration whenever possible.

Create a clean abstraction such as:

"llm.py"

so that the LLM provider can later be changed without rewriting the browser agent.

Handle:

- API errors
- timeouts
- rate limits
- invalid API keys
- empty responses
- connection failures

Show useful errors in the web UI without exposing secrets.

Browser agent

Create a Browser Use agent that receives tasks from the chat.

Example:

User:

"Open Google and search for OpenAI."

The agent should control the visible browser.

The browser must run in a virtual graphical environment:

Xvfb → XFCE → Chromium/Chrome

The agent must not use headless mode.

Configure a persistent browser profile so cookies and session state survive during the running service.

The agent should be able to:

- open URLs
- navigate
- click
- type
- press keyboard keys
- scroll
- inspect page content
- interact with forms
- select options
- wait for page changes
- handle normal JavaScript-heavy websites
- take screenshots when needed
- report task completion or failure

Implement reasonable timeouts and recovery logic.

Live browser GUI

The most important UI requirement is a live browser view.

The user must be able to see the actual Chromium desktop/browser running on Render.

Use:

- Xvfb
- XFCE
- x11vnc
- noVNC
- websockify

or an equivalent reliable implementation.

Expose the browser desktop through the application.

The frontend must contain a browser-preview panel displaying the live noVNC session.

The user must not need a separate SSH connection.

Prefer embedding the noVNC viewer directly into the application page using an iframe or the noVNC JavaScript client.

The browser preview should resize reasonably with the web page.

The noVNC endpoint must be protected by the same authenticated session as the main application. Do not expose an unauthenticated VNC password or public VNC port.

Implement reconnect logic and display the browser connection state clearly.

Task execution

Do not block the FastAPI event loop while the Browser Use agent is running.

Run agent tasks asynchronously in the background.

Only allow one active browser task per browser session unless the implementation safely supports concurrency.

If a task is already running, the UI should show:

“Agent is currently busy.”

The Stop button should attempt to cancel the active task and cleanly release resources.

Ensure cancellation does not leave orphaned processes or corrupted browser state.

The user should be able to upload files through the chat interface.

Store uploaded files in a temporary working directory.

Make uploaded files available to the browser agent when appropriate.

Limit file size and validate filenames.

Do not allow arbitrary filesystem paths from the browser or client.

Provide a safe way to download generated files from the application.

Protect downloads with authentication and prevent path traversal.
